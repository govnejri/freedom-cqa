# CQA — итоговый план

## 1. Как нас отбирают и что из этого следует

| Критерий отбора | Что делаем |
| --- | --- |
| **Точность на 10 новых диалогах против эталона организаторов** — главный | Простой сильный судья, явные трактовки, замеры на своём эталоне, вопросы организаторам по спорным местам, заморозка промптов до контроля |
| Функциональность и уникальные возможности | Фичи поверх оценки: риски, вопросы без ответа, «как надо было», второе мнение ИИ, тренажёр |
| Удобство | Один понятный путь: список → карточка → апелляция; клик по доказательству ведёт к реплике или секунде записи |
| Корректность процесса | Журнал оценки: какие запросы ушли в модель, что вернулось, время, стоимость. Живая оценка нового диалога на защите |
| Разнообразие подходов, в т.ч. локальные LLM | Один клиент для облака и локальной модели; переключатель в интерфейсе; точность обеих на эталоне |

**Локальная модель — шанс выделиться.** Организаторы прямо пишут, что сохранят в топ-50 решения на локальных LLM, а таких команд будет меньше. Для брокера это и бизнес-довод: переписка клиентов не уходит в чужое облако. Основной режим выбираем по точности на эталоне.

## 2. Продукт одной фразой

Система оценивает каждый чат и звонок по настраиваемому чек-листу, показывает доказательство к каждой оценке, даёт оспорить её и превращает оценки в решения для руководителя и обучение для оператора.

## 3. Архитектура

- **Бэкенд:** Python, FastAPI, SQLite (+FTS5 для поиска). Запуск одной командой.
- **Оценка:** один вызов модели на критерий, всё остальное — код (`docs/core-eval.md`).
- **LLM-клиент:** один OpenAI-совместимый клиент — OpenAI, Gemini (через совместимый endpoint), Ollama/vLLM. Провайдер и модель — в настройках и в интерфейсе.
- **Фронтенд:** Vanilla JS + web components, сборка в один HTML-файл, стиль Fluent. Так он встраивается в Dynamics 365 как web resource.
- **Хранение:** у каждой оценки версии чек-листа, промпта и модели, сырой ответ модели, стоимость.
- **Аудио:** бэкенд разворачивает `audio_url` (это HTML-страница со ссылкой на mp3, ссылка живёт около часа), скачивает mp3 и отдаёт его фронту с поддержкой перемотки.

Таблицы: диалоги и реплики; операторы; чек-листы и критерии с версиями; оценки и результаты по критериям; журнал вызовов модели; апелляции и решения; эталон; сигналы (причина обращения, вопросы без ответа).

## 4. Фичи

### P0 — обязательное по заданию
- Загрузка набора по `group_id`, пакетная оценка с прогрессом и повтором упавших.
- Оценка по каждому критерию: ответ, баллы, вес, обоснование, реплика-доказательство; для пропуска — проверенный участок; для N/A — причина; итог и секции.
- Список диалогов с фильтрами (язык, канал, балл, грубая ошибка).
- Карточка: транскрипт, плеер, переход от доказательства к реплике или секунде записи.
- Апелляция → решение проверяющего с причиной → пересчёт → исходная оценка, решение и итог в карточке.
- Редактор чек-листа: критерии, формулировки, веса, тип ответа, N/A, шкалы, трактовки, примеры; версии; применение к выбранным диалогам.
- **Экспорт результатов** (CSV/JSON) — для сверки жюри с эталоном.
- README с шагами запуска.

### P1 — выделяемся, дёшево
- **Журнал оценки** — прозрачность процесса: запросы, ответы модели, время, стоимость каждой оценки.
- **Локальная модель** — переключатель облако/локально, точность каждого режима на эталоне.
- **«Как надо было»** у каждого «Нет» — на языке клиента.
- **Разложение итога** — какие критерии N/A и как перераспределились веса.
- **Радар рисков** — грубые ошибки с цитатой и кнопкой «В комплаенс».
- **Вопросы без ответа** и причины обращения — по темам, со ссылками на диалоги.
- **«Требует проверки»** — перекрёстная проверка вторым провайдером, расхождение → бейдж.
- **Второе мнение ИИ** в апелляции — независимая перепроверка критерия, без показа исходного вердикта.
- **Пробный прогон и «было/стало»** при изменении критерия.
- **Качество оценки** — точность на эталоне по критериям, автотесты, стоимость.

### P2
- Прецеденты из апелляций: решение → пример в критерии → «переоценить похожие».
- Профиль оператора: баллы по критериям, три зоны роста с примерами.
- Срезы для руководителя: языки, каналы, операторы, причины обращения.
- Интерфейс на RU/KZ/EN.

### P3
- Тренажёр: ИИ играет клиента из провального диалога, ответ оценивается тем же чек-листом.
- Чат с тьютором: «почему мне снизили», «как отвечать про вывод» — по своим оценкам и лучшим ответам коллег.
- Ассистент руководителя: вопрос обычным языком → цифра и ссылки на диалоги.

## 6. Роли (4 человека; при трёх ядро берёт и бэкенд)

- **Ядро и качество:** промпты, выбор модели, метрики, автотесты, локальная модель.
- **Бэкенд:** данные, API, очередь, хранение, апелляции, экспорт, аудио.
- **Фронтенд:** все экраны, плеер, сборка в один HTML.
- **Фичи и демо:** P1–P3 поверх готовых данных, сценарий и слайды.

## 7. Протокол контрольного этапа (час 23)

1. Загрузить набор по новому `group_id`, проверить, что парсер ничего не потерял.
2. Пакетная оценка замороженной версией — результаты не правим вручную, их сверяют с эталоном.
3. Просмотреть «требует проверки» и ошибки валидатора: это сигналы, но не повод переписывать вердикты.
4. Экспорт результатов.
5. Замена критерия по запросу жюри: редактор → пробный прогон → применение. Отрепетировано заранее.

## 8. Демо — 5 минут

1. **0:00–1:00.** Дашборд: радар рисков («Скиньте деньги мне на карту»), вопросы без ответа → список → диалог.
2. **1:00–3:00.** Казахский чат: доказательство → реплика, пример N/A, разложение итога, «как надо было». Звонок: доказательство → плеер с нужной секунды. Журнал оценки: модель, время, стоимость.
3. **3:00–4:00.** Апелляция → второе мнение ИИ → решение → новый итог.
4. **4:00–5:00.** Новый критерий → пробный прогон → «было/стало» → применение ко всем. Финал: точность на эталоне, облако vs локальная модель, стоимость одной оценки.

## 9. Риски

| Риск | Что делаем |
| --- | --- |
| Трактовки организаторов отличаются от наших | вопросы организаторам в первые часы; трактовки — текст в конфиге, меняются за минуту |
| 10 контрольных диалогов не похожи на DEV | парсер терпим к новому; судья опирается на правило, а не на заученные примеры |
| Подгонка промптов под DEV | отложенные семьи сценариев; заморозка в час 20 |
| Локальная модель сильно хуже на казахском | основной режим — по точности; локальный — как опция с честной цифрой |
| Распыляемся на фичи | P1 начинаем, когда судья прошёл первый полный прогон; P3 — только по остатку времени |
| Аудио не играет в браузере | прокси через бэкенд, проверить в первый час |
| Утечка секретов (`sig=` в ссылках) | `.env`, `.gitignore`, pre-commit хук |
